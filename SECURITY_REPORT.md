# SpeakEasy — Security Audit, Vulnerability Remediation & Public Hosting Guide 🛡️

This report details the comprehensive security audit conducted on **SpeakEasy**, the vulnerabilities identified, the exact technical mitigations implemented, automated verification results, and complete instructions for hosting the application online for public access.

SpeakEasy's architecture is client-centric, interfacing with Google Gemini 2.5 Flash and browser Web Speech APIs. The audit focused on:
- Server-side file retrieval boundaries (`server.js`).
- DOM-based Cross-Site Scripting (XSS) vectors and untrusted LLM output rendering (`js/app.js`).
- Secure API credential transmission (`js/gemini.js`).
- HTTP security headers, Content Security Policy (CSP), and browser permissions.
- Input validation and length bounds.

All identified vulnerabilities have been patched, hardened, and verified with regression tests.

## 2. Vulnerability Details & Remediations

### Finding 1: Directory Traversal / Arbitrary File Disclosure in `server.js` (CWE-22)
- **Severity**: **Critical**
- **Vulnerability**: 
  The file server used `path.normalize(pathname).replace(/^(\.\.[\/\\])+/, '')`. Because URL pathnames start with a leading slash (`/`), the regex failed to strip path traversal sequences located after the slash (e.g. `/../`, `/foo/../../../Windows/win.ini`, or URL-encoded `/%2e%2e/`). This allowed attackers to escape the project directory and read arbitrary files from the server file system.
- **Remediation**:
  1. Implemented strict rejection of URL traversal sequences (`..`, `%2e`, `%2E`, `\`).
  2. Applied `path.posix.normalize` and validated that all resolved file paths strictly start with `rootDir + path.sep`.
  3. Added an explicit block against sensitive server files (`server.js`, `package.json`, `package-lock.json`) and hidden dotfiles (`.git`, `.env`).
  4. Restricted HTTP methods: strictly allow only `GET` and `HEAD` (rejecting `POST`, `PUT`, `DELETE` with `405 Method Not Allowed`).

---

### Finding 2: DOM-based Cross-Site Scripting (XSS) via Model Output & Error Strings (CWE-79)
- **Severity**: **High**
- **Vulnerability**:
  - `fluencyVocab.fillerAnalysis` (generated by the AI model) was interpolated into an `.innerHTML` assignment without HTML entity escaping. If malicious or unexpected content was emitted, scripts could execute in the user's browser and access `localStorage` (which stores the user's Gemini API key).
  - In `handleGenerateReport`, error messages (`err.message`) were interpolated directly into `this.reportLoading.innerHTML` along with an inline `onclick="..."` attribute.
  - The initial `escapeHtml` function did not escape single quotes (`'`), which could allow attribute-based injection if values were wrapped in single quotes.
- **Remediation**:
  1. Enhanced `escapeHtml()` to comprehensively escape `&`, `<`, `>`, `"`, and `'` (`&#39;`).
  2. Replaced `innerHTML` in the error handler with safe DOM construction (`document.createElement`, `textContent`, and event listeners), removing inline script handlers.
  3. Sanitized all interpolated model properties, filler keys, and metric counts before DOM insertion.

---

### Finding 3: Sensitive API Key Transmitted in URL Query Parameter (CWE-598 / CWE-200)
- **Severity**: **High**
- **Vulnerability**:
  Calls to the Google Gemini API passed the key in the URL query string:
  `https://generativelanguage.googleapis.com/...:generateContent?key=YOUR_API_KEY`
  Query strings are routinely logged in browser history, proxy server logs, firewall/gateway access logs, and can leak via `Referer` headers when external links are clicked.
- **Remediation**:
  Updated `js/gemini.js` in both `generateReply` and `analyzeConversation` to pass the key via Google's official HTTP header:
  ```javascript
  headers: {
    'Content-Type': 'application/json',
    'x-goog-api-key': this.apiKey
  }
  ```
  The request URL remains clean: `https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent`.

---

### Finding 4: Missing HTTP Security Headers & Content Security Policy (CWE-693)
- **Severity**: **Medium**
- **Vulnerability**:
  The application had no Content Security Policy (CSP) or standard defensive headers, leaving it susceptible to clickjacking, MIME sniffing, and unconstrained script execution.
- **Remediation**:
  Added the following security headers in `server.js` and matching `<meta>` tags in `index.html`:
  - `Content-Security-Policy`: Restricts scripts to `'self'`, fonts to Google Fonts (`fonts.gstatic.com`), styles to `'self'` and Google Fonts, images to `'self'` and `data:`, and outgoing network requests strictly to `'self'` and `https://generativelanguage.googleapis.com`.
  - `X-Content-Type-Options: nosniff`: Prevents browsers from MIME-sniffing responses.
  - `X-Frame-Options: DENY`: Prevents the app from being embedded in iframes (anti-Clickjacking).
  - `Referrer-Policy: strict-origin-when-cross-origin`: Restricts referrer data to the origin on cross-origin requests.
  - `Permissions-Policy: microphone=(self), camera=(), geolocation=()`: Restricts microphone access exclusively to the origin, preventing third-party abuse.

---

### Finding 5: Unbounded Input Length / Potential Resource Denial of Service (CWE-400)
- **Severity**: **Medium**
- **Vulnerability**:
  User inputs (both typed and transcribed) had no maximum length boundary. An excessively large payload could exhaust browser memory, cause token overflow errors, or generate high latency.
- **Remediation**:
  - Enforced `maxlength="1000"` on `<input id="text-input">` in `index.html`.
  - Added `.slice(0, 1000)` truncation and sanitization in `processUserUtterance` in `js/app.js` before dispatching to the API or saving to storage.

## 4. How to Host SpeakEasy Online for Everyone 🌐

Because SpeakEasy is built as a clean, lightweight web app without external build tool dependencies, you can deploy it publicly in minutes.

> [!IMPORTANT]
> **HTTPS is Required for Microphone Access**: The Web Speech API (`webkitSpeechRecognition`) requires a secure HTTPS connection when hosted online. All the platforms recommended below automatically provide free SSL/HTTPS certificates.

---

### Deployment Model Overview

You have two main hosting options:

#### Model A: Client-Side "Bring Your Own Key" (Recommended & Zero Cost)
- **How it works**: You host the static frontend on a free static host (Vercel, Netlify, Cloudflare Pages, GitHub Pages).
- **Security & Cost**: Visitors open the app and paste their own free Gemini API key in Settings (stored safely in their personal browser `localStorage`).
- **Advantage**: Zero server hosting costs, zero API billing risk for you, and infinite scalability.

#### Model B: Shared Key via Serverless / Node Proxy
- **How it works**: You host the Node.js server (e.g. on Render, Railway, or Vercel Serverless Functions) with a `GEMINI_API_KEY` environment variable on the server.
- **Advantage**: Visitors can talk immediately without providing their own key.
- **Precaution**: You should implement IP rate limiting (e.g. 20 messages per user per hour) so visitors do not exhaust your API quota.

---

### Platform 1: Vercel (Fastest & Free HTTPS)

1. Create a free account at [Vercel.com](https://vercel.com).
2. Push your project folder to a GitHub repository:
   ```bash
   git init
   git add .
   git commit -m "Initial SpeakEasy release"
   git remote add origin https://github.com/YOUR_USERNAME/speakeasy.git
   git branch -M main
   git push -u origin main
   ```
3. In Vercel, click **"Add New Project"** and select your `speakeasy` repository.
4. Leave build settings as default (`Framework Preset: Other`, `Root Directory: ./`).
5. Click **"Deploy"**.
6. Your app will be live at `https://speakeasy-yourname.vercel.app` with free automated HTTPS!

---

### Platform 2: Netlify (Drag & Drop or Git)

#### Method A: Instant Drag & Drop (No Git needed!)
1. Log in to [Netlify.com](https://www.netlify.com).
2. Go to **Sites > Add new site > Deploy manually**.
3. Drag the `d:\project_for_JOB\EasySpeak` folder and drop it into the upload box.
4. Netlify will deploy it immediately and provide an HTTPS URL like `https://speakeasy-chat.netlify.app`.

#### Method B: Git Integration
1. Connect your GitHub account.
2. Select the `speakeasy` repo and click **Deploy Site**.

---

### Platform 3: GitHub Pages (100% Free Forever)

1. Push your repository to GitHub:
   ```bash
   git init
   git add .
   git commit -m "SpeakEasy voice assistant"
   git branch -M main
   git remote add origin https://github.com/YOUR_USERNAME/speakeasy.git
   git push -u origin main
   ```
2. On your GitHub repository page:
   - Click **Settings** > **Pages** (in the left sidebar).
   - Under **Build and deployment > Source**, choose `Deploy from a branch`.
   - Select `main` branch and `/ (root)` folder.
   - Click **Save**.
3. In 1–2 minutes, your app will be accessible at:
   `https://YOUR_USERNAME.github.io/speakeasy/`

---

### Platform 4: Render / Railway (For Running `server.js`)

If you prefer hosting the Node.js backend server with environment variables:

1. **On Render ([render.com](https://render.com))**:
   - Click **New > Web Service**.
   - Connect your GitHub repo.
   - Set **Runtime** to `Node`.
   - Set **Build Command** to empty or `npm install`.
   - Set **Start Command** to `npm start`.
   - (Optional) In **Environment Variables**, add `GEMINI_API_KEY` if you want a centralized server key.
   - Click **Create Web Service**. Render provides a free `https://speakeasy.onrender.com` domain with automatic HTTPS.

2. **On Railway ([railway.app](https://railway.app))**:
   - Click **New Project > Deploy from GitHub repo**.
   - Railway automatically detects `package.json` and runs `npm start`.
   - In the service settings, click **Generate Domain** to get your public HTTPS URL.

---

### Platform 5: Cloudflare Pages

1. Log in to the [Cloudflare Dashboard](https://dash.cloudflare.com/) and go to **Workers & Pages > Pages**.
2. Connect your GitHub account and pick the `speakeasy` repository.
3. In Build settings, leave **Build command** empty and **Output directory** set to `/`.
4. Click **Save and Deploy**.
5. Cloudflare distributes your app across 300+ global edge data centers with free HTTPS and DDoS protection.

## 5. Security Best Practices for Production

When sharing your app publicly:
1. **Never commit your personal API key to git**: `localStorage` is kept strictly on the client side and is never stored in files or Git commits.
2. **Always enforce HTTPS**: Web browsers will block microphone audio capture on unencrypted HTTP connections outside of `localhost`.
3. **Keep CSP Active**: The Content Security Policy in `server.js` and `index.html` ensures that no unauthorized third-party scripts or tracking domains can execute or exfiltrate conversation data.
